# F1 Title Margins

Durable rules for coding agents working in this repository.

## Architecture

- A static site: pinned F1DB release → deterministic Python pipeline (`pipeline/`) → committed
  `data/seasons.json` → React + strict TypeScript + ECharts + Vite (`src/`) → static hosting.
- There is no runtime backend, API, database service, authentication or user account system. Do
  not add one.

## Product scope

- v1 is a historical Formula 1 Drivers' Championship product: the champion's margin over the
  runner-up in each completed season.
- No speculative feature expansion. Work beyond the current version requires an explicit
  version/product contract from the owner first.

## Analytical invariants

- The F1DB release pinned in `data/f1db-release.json` is the authoritative input.
- Final championship totals come from F1DB's recorded final standings. Never reconstruct them by
  summing race results.
- Preserve championship points exactly, fractional totals included; the pipeline never passes
  them through floats.
- Do not silently invent historical relationships the source does not support. If a relationship
  the work needs does not exist cleanly in the source, stop and report.

## Generated data

- `data/seasons.json` is generated by the pipeline and intentionally tracked. Never edit it by hand.
- It changes only through deterministic regeneration against the explicit pin. Rebuilding from an
  unchanged pin must leave it byte-identical.
- An unexplained diff in a historical season is a stop condition, not something to commit.

## Verification

- `.github/workflows/ci.yml` is the canonical full release-verification
  sequence. Do not duplicate the full sequence elsewhere; README commands are
  convenience commands for humans.

## Git safety

- Never force-push shared or release branches, and never rewrite pushed history.
- Never weaken, skip or delete a test to make it green, and never bypass release checks.
- Keep accidental generated, cache and build artifacts (`dist/`, `.cache/`, `node_modules/`) out
  of commits.

## Scope discipline

- Use the smallest robust change that addresses the agreed risk. Elegance is a requirement here.
- Delete a superseded approach rather than leaving dormant machinery behind.
- No speculative abstractions, duplicate configuration or unrequested clean-up.
- When blocked, stop and report rather than broadening scope.
